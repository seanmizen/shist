# 1.1.0 worklog

A record of what was done for 1.1.0 and why, to write up later. The
user-facing summary is in [CHANGELOG.md](../CHANGELOG.md).

Work happened in three passes after an audit of 1.0.1:

1. **§1 correctness**: the eleven bugs from the audit.
2. **§2 speed**.
3. **§3 "top-tier library" items**: tests, module path, layout, error handling,
   colour, README.

## Speed

Benchmark fixture: 300,000 zsh EXTENDED_HISTORY entries, 20MB. Machine:
Apple Silicon laptop. Tool: `hyperfine -N`, stdout to /dev/null.

| run | 1.0.1 | after §1 | 1.1.0 |
|---|---|---|---|
| all entries | 1.110 s | 0.758 s | **0.053 s** |
| `-n 20` | 0.298 s | 0.277 s | **0.024 s** |
| `-g "msg 1234"` | 0.302 s | – | **0.033 s** |
| all entries, `FORCE_COLOR=1` | – | – | 0.054 s |
| `-n 20` on 3M entries (200MB) | – | – | 0.193 s |

With stderr on a terminal, 1.0.1's full run was about 1.47 s: it coloured
output going to /dev/null and made a terminal-check system call for every
colour token on every line.

`go test -bench` (`make bench`):

- Parsers run at about 1.0–1.3 GB/s on 100k-entry synthetic files. Allocations
  come only from multi-line commands (3 per multi-line entry).
- `Template.Append` takes 92 ns per entry with 0 allocations.
- End to end (`BenchmarkMain`, 100k entries): 15 ms for all entries, 4.7 ms
  for `-n 20`.

What made the difference, roughly by impact:

1. The template was re-expanded with a regex, and `term.IsTerminal` called
   for each `%C` token, for every entry. Now `format.Compile` runs once and
   the terminal check happens once.
2. Output is appended into one byte buffer and written in 64KB chunks
   (1.0 used `fmt.Println` per line).
3. The whole file is read with `os.ReadFile` and lines are substrings, so
   single-line commands need no allocations. The zsh and bash headers are
   parsed by hand instead of with a regex.
4. `-g` with a plain-text pattern uses `strings.Contains`
   (`regexp.LiteralPrefix` tells us when that's safe).
5. Date filters compare int64 seconds instead of building a `time.Time` per entry.

**Considered and not done: reading from the end of the file for `-n`.**
`%i` and `-min-index`/`-max-index` number entries from the start of the
file, so the whole file must be scanned to know the numbering anyway.
Counting entries correctly means repeating each parser's rules (continuations,
dropped blank commands), which is an easy source of off-by-one bugs. After the
changes above, `-n 20` on 300k entries takes 24 ms, so it isn't worth it. If
it's ever needed, the way to do it is to parse only the tail when neither `%i`
nor index filters are used.

## Layout and module

Before: `src/main`, `src/nix` (CLI + all parsers + printing in one 490-line
file), `src/model`, `src/ui`; module `shist`.

After, with module `github.com/seanmizen/shist`:

```
main.go                     os.Exit(cli.Main(version, cli.OSEnv()))
internal/history/           Entry, Format interface, Detect, Load
  zsh.go bash.go fish.go powershell.go   one parser each
  lines.go                  zero-alloc line iterator + entry builder
internal/format/            Compile(template) → Template.Append(buf, entry)
  color.go                  git-style %C specs, ColorEnabled
internal/cli/               flags + env defaults, filters, errors, help text
```

- `main.go` is at the root rather than in `cmd/shist`, so the install command
  is `go install github.com/seanmizen/shist@latest`. With `cmd/shist` it would
  be `…/shist/cmd/shist@latest`. This differs from the audit's suggestion.
- The packages are `internal/`, so there's no public Go API to keep stable.
  If shist ever wants to be a library too, `history` is the package to promote.
- `Format.Parse(data string) []Entry` takes the whole file as a string and
  returns no error. The only way to fail is I/O, and that's handled in `Load`.
  It also makes the parsers easy to fuzz.

## Error handling

- `cli.Main(version, Env) int`. `Env` holds args, stdout, stderr and
  `LookupEnv`, so tests run the whole CLI in-process with fake env and
  buffers. Nothing calls `os.Exit` except `main`.
- `usageError` → exit 2 plus `Run 'shist -h' for usage.`; everything else →
  exit 1. Messages are prefixed `shist: `.
- The FlagSet uses `ContinueOnError` with output discarded. shist prints its
  own messages, so Go's flag defaults dump doesn't appear on every typo.
- Help is hand-written (`help.go`) so aliases (`-g, -grep`), tokens and env
  vars read properly. `TestHelpMentionsEveryFlag` fails if a flag is added
  without documenting it.

## Colour

- A spec is space-separated words: attributes (`bold dim italic ul blink
  reverse strike`) and up to two colours (foreground, background). A colour
  is a name, `bright<name>`, `default`, `0`–`255`, or `#rrggbb`/`rrggbb`.
- An unknown word makes the whole spec produce no colour, the same as 1.0.
  This kept the no-breaking-changes promise. git errors instead;
  **open question** whether 2.0 should too.
- Precedence: `-no-color` / `NO_COLOR` / `SHIST_*NO_COLOR` → off; else
  `FORCE_COLOR` (anything but empty, `0` or `false`) → on; else on only if
  stdout is a terminal (plus the old Windows-terminal heuristics).

Fuzzing ran for 30 s on the parsers (2.8M execs) and 15 s + 10 s on
templates and colour specs, with no failures.

## Behaviour changes to call out in release notes

These are all bug fixes or stricter checks; no flag was removed or renamed:

- `-n` applies after the other filters.
- Dates are local; `-max-date` is inclusive of the day or minute.
- Stray positional args and bad numeric env vars are errors (exit 2).
- `-h` goes to stdout and exits 0.
- `%%` is now a literal `%` (before, `%%d` printed `%` followed by the date).
- No double space in multi-line output.

## Open questions / next

- Should unknown `%C(...)` words be an error, like git? That would be a
  breaking change, so 2.0 at the earliest.
- CI only runs vet and test on tag pushes. A workflow on push and PRs (plus
  `golangci-lint` and a short fuzz) is the obvious next step.
- GoReleaser could replace `make release` and push to the Homebrew tap
  automatically.
- Features from the audit not done yet: `--reverse`, `--unique`, relative
  dates (`--since 2h`), `--json`, `-0`, `--shell` override, shell completions,
  man page.
- The README example output in the intro is illustrative, not captured from
  a real run.
